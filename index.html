01 • visão executiva

O que você realmente precisa saber para a prova

WBS

Decomposição hierárquica do escopo total do projeto em componentes menores e gerenciáveis, orientada a entregas/resultados.

100%

Os filhos devem representar 100% do pai; a WBS contém todo o trabalho do escopo e não inclui trabalho fora dele.

Work package

Nível mais baixo da WBS, suficientemente gerenciável para estimar, atribuir, executar, acompanhar e medir.

★
Regra mental de prova: pergunte primeiro “isto é uma entrega/resultado ou é uma atividade?” Depois pergunte “os filhos cobrem 100% do pai?”
02 • conceito

WBS segundo a visão do PMI

O PMI trata a WBS como uma decomposição hierárquica do trabalho/escopo do projeto. A boa prática é que a estrutura seja deliverable-oriented: ela organiza o que o projeto precisa produzir, entregar ou concluir, em vez de ser simplesmente uma lista de ações.

O que a WBS responde

  • Quais resultados e entregas compõem o escopo?
  • Quais subentregas formam cada resultado?
  • Qual é a menor unidade útil para controle?
  • Existe algo faltando ou algo que não deveria estar no projeto?
❌ “Codificar módulo de login”ação / atividade
✅ “Módulo de autenticação implementado”resultado / entrega
Atualização de referência: o PMBOK® Guide — 8ª edição foi publicado em novembro de 2025. O PMI informa que a 8ª edição mantém princípios e domínios da 7ª, mas reintroduz orientação de processos de forma evoluída e não prescritiva. Para o exame lançado em julho de 2026, use o ECO 2026 junto com o PMBOK 8.

04 • princípio central

Regra dos 100%

Σ filhos = 100% do pai

✅ Exemplo

1. Plataforma de vendas
├─ 1.1 Frontend
├─ 1.2 Backend
├─ 1.3 Banco de dados
└─ 1.4 Implantação

Se essas quatro parcelas juntas representam todo o escopo do elemento “Plataforma de vendas”, o nível está coerente.

❌ Incompleto

1. Plataforma de vendas
├─ 1.1 Frontend
├─ 1.2 Backend
└─ 1.3 Banco de dados

Se também existe segurança, infraestrutura e implantação dentro do escopo, algo ficou de fora.

100%
O 100% vale em todos os níveis. A regra não serve apenas para a raiz. Os filhos de cada componente devem somar exatamente o trabalho representado pelo pai.
05 • decomposição

Como decompor sem transformar a WBS em cronograma

  1. Comece pelo resultado do projeto.Ex.: “Sistema web de gestão implantado e aceito”.
  2. Identifique grandes entregas.Ex.: aplicação, dados, integrações, implantação, documentação.
  3. Quebre cada entrega em subentregas.Use componentes que façam sentido para a solução.
  4. Repita até chegar a unidades gerenciáveis.O nível mais baixo útil torna-se candidato a work package.
  5. Faça o teste da entrega.O nome deve descrever um resultado claro, não apenas uma ação.
  6. Faça o teste dos 100%.Procure lacunas, excesso e sobreposição.
Quando parar?
Quando continuar decompondo deixar de aumentar o controle ou quando o componente já for pequeno o bastante para ser estimado, atribuído, executado, monitorado e medido com clareza.
06 • work package

Work package: o nível operacional da WBS

O work package é o nível mais baixo da WBS. Ele representa um pedaço de escopo suficientemente pequeno para ser administrado, sem exigir que a WBS já seja uma lista de tarefas.

Estimarcustos / esforço / recursos
Atribuirresponsabilidade
Controlarprogresso e desempenho
Medirresultado / aceitação
Não confunda: work package ≠ atividade. Um work package pode ser decomposto em várias atividades no planejamento do cronograma.
07 • control account

Control account

É um ponto de controle gerencial em que escopo, orçamento e cronograma se integram para acompanhamento de desempenho. Work packages ficam dentro de control accounts.

WBS
└─ Control Account
   ├─ Work Package A
   ├─ Work Package B
   └─ Work Package C

O conceito aparece também em materiais clássicos do PMI associados a EVM. Em uma questão, pense em control account como “ponto onde o trabalho é gerenciado e medido”, não como uma tarefa.

08 • dicionário

WBS Dictionary

A árvore mostra a estrutura; o dicionário elimina ambiguidades. Para cada elemento relevante, o projeto pode registrar informações como descrição do escopo, critérios de aceitação, responsável, marcos, recursos, premissas, restrições e outras informações úteis ao controle.

11 • método do zero

Como construir uma WBS sozinho

1

Leia o objetivo sem pensar em tarefas

Extraia produto, serviço, resultado, clientes e critérios de sucesso.

2

Liste as entregas principais

Use substantivos/resultados: “API integrada”, “ambiente de produção configurado”, “usuários treinados”.

3

Decomponha por lógica consistente

Dentro de cada ramo, escolha um critério coerente: componente do produto, fase, subentrega, ambiente etc. Evite misturar critérios sem necessidade.

4

Teste o nível de gerenciabilidade

Quando o item puder ser estimado, atribuído e controlado com clareza, você está próximo de um work package.

5

Teste 100%, exclusividade e fronteiras

Sem lacunas, sem trabalho fora do escopo e sem o mesmo trabalho contado duas vezes.

6

Só depois derive atividades

Retire os work packages da árvore e determine o que precisa ser feito para produzi-los.

15 • prova

Pegadinhas que você deve reconhecer instantaneamente

“A WBS lista as atividades na ordem de execução.”❌ Não. Isso é lógica de cronograma.
“Todos os ramos precisam ter o mesmo número de níveis.”❌ Não. A profundidade depende da necessidade de gerenciamento.
“Mais detalhes sempre significam uma WBS melhor.”❌ Não. O excesso de decomposição pode gerar complexidade sem ganho de controle.
“Work package é sinônimo de atividade.”❌ Não. Atividades podem ser derivadas de work packages.
“A WBS pode conter qualquer trabalho que ajude o projeto.”❌ Não. A regra dos 100% impede trabalho fora do escopo.
“Se um usuário pedir algo novo, basta colocar na WBS.”❌ Não quando isso representar mudança de escopo aprovado; use o processo de mudança adequado.
“Project Scope e Product Scope são a mesma coisa.”❌ Não. Produto = características/funções; projeto = trabalho necessário para produzir o resultado.

O que estudar além da WBS

Escopo e requisitos

Para saber de onde a WBS nasce e como evitar incluir trabalho indevido.

Schedule

Para dominar a transição WBS → atividades → dependências → duração → cronograma.

Change control

Para reconhecer questões em que alguém tenta alterar a baseline sem passar pelo mecanismo correto.

Cost / EVM

Para compreender control accounts, baselines de desempenho e integração entre escopo, prazo e custo.

Risk

Porque decomposição clara aumenta visibilidade sobre pontos de incerteza.

Agile / Hybrid

O PMP atual cobra cenários adaptativos e híbridos; não trate WBS como assunto exclusivamente waterfall.

Objetivo de domínio: ao receber um enunciado novo, você deve conseguir desenhar a primeira versão da WBS sem copiar um modelo, justificar onde parou e apontar o que pertence ao cronograma em vez da WBS.
